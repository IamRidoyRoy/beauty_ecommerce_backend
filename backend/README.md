# Beauty E-commerce Backend API

Production-oriented Django/DRF backend for a Next.js storefront and React/Redux management dashboard. Native simple products and real variable products are first-class inventory targets.

Read `../ARCHITECTURE.md` first for the ERD, product architecture, stock architecture, lifecycles, API map, and RBAC matrix.

## Runtime

- Python 3.10+
- Django 5.2 LTS
- Django REST Framework 3.18
- PostgreSQL production / SQLite development
- Redis production / LocMemCache development
- Celery + Beat
- SimpleJWT + refresh blacklist
- django-filter
- drf-spectacular
- django-cors-headers
- Pillow

## Local development

```bash
python -m venv .venv
# Windows: .venv\Scripts\activate
# Linux/macOS: source .venv/bin/activate
pip install -r requirements.txt
python manage.py makemigrations
python manage.py migrate
python manage.py seed_full_demo
python manage.py runserver
```

Development defaults to SQLite, LocMemCache, console notifications, and eager Celery. Redis is not required.

Demo super admin:

```text

```

## Production

Copy `.env.example` to `.env`, use a strong secret, PostgreSQL `DATABASE_URL`, Redis `REDIS_URL`, explicit hosts/origins, and provider credentials. Then:

```bash
python manage.py migrate
python manage.py collectstatic --noinput
gunicorn config.wsgi:application --bind 0.0.0.0:8000
celery -A config worker -l info
celery -A config beat -l info
```

Or use the included Dockerfile/docker-compose services.

## Important service boundaries

Critical business operations live in `services.py`, not `ModelViewSet` methods:

- cart add/update and inventory-target validation
- checkout
- stock reserve/release/consume/increase/decrease/adjust/transfer
- purchase receiving
- order transitions
- coupon/promotion calculation
- returns/refunds
- payment idempotency boundary
- notification queueing

Query-heavy read paths and reports live in `selectors.py` and use `select_related`, `prefetch_related`, annotations, aggregation, `Exists`, and `Subquery` where appropriate.

## External providers

Pathao, Steadfast, RedX and Google auth are explicit adapter extension points. The repository does not pretend to call live providers without credentials. Payment webhooks have an idempotency event table/service boundary ready for provider-specific signature verification and mapping.

## Migrations note

This source bundle was generated in an execution environment where Django packages could not be downloaded, so autogenerated migration files were not fabricated by hand. After dependency installation, run `python manage.py makemigrations` once, review the generated SQL, commit those migrations to your deployment repository, then run the full test/check/schema commands above before release.

## District / Thana delivery data

A dedicated `apps.delivery` module is included for Bangladesh delivery geography.
The original supplied source files are bundled unchanged at:

```text
apps/delivery/data/city.json
apps/delivery/data/thana.json
apps/delivery/data/city_legacy.py
```

After updating this project, create/apply the new delivery tables and import the data:

```bash
python manage.py makemigrations delivery
python manage.py migrate
python manage.py import_delivery_data
```

The command is idempotent and can safely be run again. Use `--reset` only when you intentionally want to clear existing city/thana rows before reimporting:

```bash
python manage.py import_delivery_data --reset
```

The import creates/updates these pricing modules:

```text
Inside Dhaka   ৳60
Subarea        ৳90
Outside Dhaka  ৳120
```

The supplied `city.json` marks Dhaka with delivery module `1` and the other supplied cities with module `2`. It does **not** identify which specific thanas should use the third `Subarea` price. Therefore the importer does not guess. Assign `Subarea` to the required Thana rows using Django Admin or the management API. A thana-level module overrides its district; otherwise it inherits the district module.

Public endpoints used by checkout:

```text
GET /api/v1/districts/
GET /api/v1/districts/{district_id}/thanas/
GET /api/v1/thanas/?district={district_id}
GET /api/v1/delivery-modules/
GET /api/v1/delivery-charge/?district={district_id}&thana={thana_id}
```

Checkout now submits district/thana IDs:

```json
{
  "name": "Customer Name",
  "phone": "017XXXXXXXX",
  "district": 1,
  "thana": 17,
  "address": "House 10, Road 5",
  "payment_method": "cod"
}
```

The backend validates that the selected thana belongs to the selected district and calculates the delivery charge server-side. The order snapshot keeps the district/thana names, IDs, delivery-module code/name, and the historical charge.

### Existing phone checkout behavior

Anonymous checkout is no longer blocked when the phone already belongs to an account. The order is allowed and linked to that account, but **no JWT is returned and the customer is not automatically authenticated**. To avoid unauthenticated changes to the existing account, the guest-provided address is kept on the order snapshot and is not added to that user's saved address book. New phone numbers still create the customer account only after the order succeeds and return access/refresh tokens.

## OTP login troubleshooting

OTP login requires the accounts and SimpleJWT blacklist tables to be migrated:

```bash
python manage.py migrate
python manage.py migrate token_blacklist
```

Run the OTP regression test with:

```bash
python manage.py test apps.accounts.tests.test_otp
```

In development (`DEBUG=True`), OTP request remains usable even when an SMS/Celery provider is unavailable; the response includes `development_otp`. Unexpected HTTP 500 responses include the exception type/detail only in development so the root cause can be diagnosed without leaking internals in production.


## Development OTP from Django Admin

In local development (`DEBUG=True`), requesting an OTP creates an `OTPChallenge` row and stores the readable six-digit code in `debug_code` **only for development**. Verification still uses the HMAC hash.

1. Run `python manage.py makemigrations accounts && python manage.py migrate`.
2. Request an OTP from the storefront or `POST /api/v1/auth/otp/request/`.
3. Open `/admin/accounts/otpchallenge/` and copy the newest `debug_code`.
4. Enter that code in the storefront verification form.

Production never stores a readable OTP (`debug_code` remains empty).

The custom OTP throttle supports the configured `5/10min` rate. This avoids DRF's stock `SimpleRateThrottle` parser crash (`KeyError: '1'`) for numeric time windows.


## Existing customer checkout verification toggle

A singleton `CheckoutSettings` model is available in Django Admin under **Common → Checkout settings**.

- ON (default): existing-phone guest checkout places the order, then requires OTP/password before full account access.
- OFF in development: after a successful order, the backend immediately returns JWT for the existing account and the storefront signs the customer in.
- OFF in production: full-account JWT is intentionally not issued from phone knowledge alone.

After updating an existing project, create/apply the new model migration:

```bash
python manage.py makemigrations common
python manage.py migrate
```

## Product image workflow

The catalog supports multiple product and variant images. Exactly one image in each gallery scope can be marked `is_primary=true`.

Dashboard bulk upload:

```http
POST /api/v1/admin/images/bulk-upload/
Content-Type: multipart/form-data

product=<product id>
variant=<optional variant id>
primary_index=0
images=<file 1>
images=<file 2>
...
```

`primary_index` is zero-based within the uploaded files and becomes the storefront Feature Image for a base product gallery (or the primary image for a variant gallery). If the first gallery has no primary image and `primary_index` is omitted, the first uploaded image is promoted automatically. Deleting the current primary image promotes the next image in gallery order.

Uploaded media is served from `MEDIA_URL=/media/` in development. The customer storefront should point `NEXT_PUBLIC_API_BASE_URL` at this Django host; media defaults to the same host automatically.
